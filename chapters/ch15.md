# 第 15 章 Envoy Gateway 与 Kubernetes Gateway API

## 15.1 角色分离是 API 的一部分

Gateway API 将基础设施提供方、集群运营者与应用开发者的职责分开。GatewayClass 描述控制器类别，Gateway 描述监听器等基础设施入口，HTTPRoute 描述 HTTP 路由规则。Envoy Gateway 作为实现，将受支持的资源转成 Envoy 数据面配置。

这种模型使应用团队可以在授权范围内管理路由，而运营团队控制入口、证书与跨命名空间规则。它比把所有配置塞进同一个文件更利于权限分工，但需要明确谁拥有每个资源。

## 15.2 一个最小路由片段

下面是 Gateway API 的路由示例。它需要集群中已安装匹配的 CRD、控制器、名为 `public` 的 Gateway，以及命名空间内的 `orders` Service；本书未将此片段作为已部署集群的验收结果。

``` yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: orders
spec:
  parentRefs:
    - name: public
  hostnames:
    - api.example.com
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /api/orders
      backendRefs:
        - name: orders
          port: 8080
```

对象创建成功不等于流量成功。先看 Route 的 Accepted、ResolvedRefs 等状态及原因，再看 Gateway 的条件、Service endpoint、数据面路由和请求日志。跨命名空间的后端引用还需满足 ReferenceGrant 等授权规则，不能把权限失败当作路由算法失败。

## 15.3 标准化范围与实现扩展

Gateway API 提供通用模型，但限流、外部鉴权、策略附着和高级 Envoy 特性可能依赖实现提供的扩展资源。使用扩展时应记录其 apiVersion、作用域、冲突处理与升级策略。支持 HTTPRoute 并不代表所有扩展功能可移植。

ShenYu 的选择器规则与 Gateway API 的路由资源无法逐字段一一映射。迁移应从业务意图重建：哪些域名与路径需要什么身份、路由到什么服务、采用哪种预算和故障行为。再根据控制器能力决定使用标准字段、扩展策略或自定义插件。
