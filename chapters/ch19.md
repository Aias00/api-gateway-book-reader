# 第 19 章 实现一个可验证的最小网关内核

## 19.1 为什么选择一个小模型

完整生产网关需要 HTTP 解析、连接池、TLS、协议升级与大量运维能力，无法用几十行代码可靠替代。本书实验刻意聚焦策略内核：请求上下文、确定性路由、令牌桶、熔断器、不可变配置快照和版本发布。

配套 `examples/gateway_core.py` 使用 Python 标准库，`examples/test_gateway_core.py` 提供确定性单元测试。测试通过手动传入单调时间，避免 sleep 导致不稳定。实验的契约与 ShenYu 源码契约明确分开，不要求算法逐行一致。

## 19.2 核心不变量

路由必须有确定性赢家，且 `/api` 不误中 `/apix`。令牌桶不允许透支，也不能补充超过容量。熔断器打开期间拒绝请求，半开只允许一个在途探测。配置发布忽略旧版本，拒绝重复路由 id 与非法上游，回滚内容使用新版本号。

请求在入口捕获快照后，即使发布新配置，该请求仍使用旧快照完成。这使一次请求的决策自洽。新请求使用新快照，因此配置切换期间短暂共存两个版本是有意设计。

## 19.3 实验步骤

在源码目录执行：

``` sh
python3 -m unittest discover -s examples -v
python3 examples/gateway_core.py
```

第二个命令打印路由匹配、连续令牌消费以及配置更新后的结果。读者可修改规则优先级，观察重叠规则的赢家；将补充速率减半，验证等待时间；在熔断器失败阈值达到后，推进时间到恢复点，验证单探测限制。

这些实验没有启动真实 HTTP 代理，不包括 TLS、网络故障和并发生产实现。移植到生产前，应补充并发同步、持久化、外部依赖、协议集成和资源管理。小模型的价值是暴露设计不变量，不能因为通过单元测试就宣称实现了完整网关。

## 19.4 把模型连接回 ShenYu

在 ShenYu 中，对应的链入口是每请求创建的 `DefaultShenyuPluginChain`；匹配由插件基类与策略实现协作完成；策略状态由具体插件管理；配置通过同步体系更新本地数据。实验将这些职责放在少数类中，是为了可观察性，而不是替项目重新定义架构。

读者可进一步写一个只记录路由与配置版本的 ShenYu 插件，在测试环境中观察正常完成、拒绝、错误和取消路径。编译依赖必须固定在目标 ShenYu 版本，不在本书中提供假定跨版本通用的插件包。

**思考题。** 为什么使用真实等待时间测试令牌补充，比注入时间更容易产生偶发失败？
